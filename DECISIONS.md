# DECISIONS.md — Зафиксированные архитектурные решения

Все решения в этом документе считаются окончательными.
Пересмотр возможен только по явному запросу.

---

## ADR-001 | 2026-06-30
### Приложение — голосовой пульт, не плеер

**Решение:** DJ Assistant управляет сторонними приложениями через Android MediaSession API. Собственный плеер, MediaStore-сканер, база медиатеки — отсутствуют.

**Причина:** Пользователь уже использует предпочитаемый плеер (Spotify, AIMP, VK Музыка и т.д.). Приложение не должно конкурировать с ними.

## ADR-002 | 2026-06-30
### Multi-module Gradle: 6 модулей

**Решение:** `app`, `core`, `data`, `feature`, `service`, `ui`

**Причина:** Достаточно для принудительного разделения слоёв без излишней сложности. Параллельная компиляция Gradle. Чёткие границы зависимостей.

**График зависимостей:**
```
app → [core, data, feature, service, ui]
ui → [core, data, feature, service]
service → [core, feature]
feature → [core, data]
data → [core]
core → []
```

## ADR-003 | 2026-06-30
### Vosk вместо Porcupine для MVP

**Решение:** Vosk обрабатывает и wake word и команду в одном распознавании. Пользователь говорит "Диджей, пауза" целой фразой. Porcupine добавляется в будущем как отдельный детектор.

**Причина:** Упрощает MVP. Vosk бесплатен, имеет малую модель для русского (~50MB), поддерживает Grammar Mode.

---

## ADR-004 | 2026-06-30
### Grammar Mode Vosk (ограниченный словарь)

**Решение:** Vosk работает только в пространстве заранее известных фраз. Грамматика генерируется автоматически из `CommandRegistry`.

**Причина:** Меньше CPU, меньше ложных срабатываний, выше точность для известных команд.

**Ключевое свойство:** `GrammarBuilder.build()` итерирует `registry.allCommands` — добавление новой команды автоматически добавляет её в грамматику.

## ADR-005 | 2026-06-30
### Command Pattern + Registry

**Решение:** Каждая команда — отдельный класс, реализующий `DjCommand`. Все команды хранятся в `CommandRegistry`. Маршрутизация через `CommandDispatcher`.

**Причина:** Добавление новой команды = создать 1 файл + зарегистрировать в `AppModule`. Ни `IntentRecognizer`, ни `CommandDispatcher`, ни другие команды не затрагиваются.

## ADR-006 | 2026-06-30
### Отдельный слой Intent (DjIntent)

**Решение:** `IntentRecognizer` (текст → `DjIntent`) отделён от `CommandDispatcher` (`DjIntent` → выполнение).

**Причина:** Разделяет "что хочет пользователь" от "как это выполнить". Параметризованные команды ("тише на 20%") добавляются в `IntentRecognizer` без изменения слоя команд.

## ADR-007 | 2026-06-30
### Две реализации MediaRemote

**Решение:**
- `KeyEventMediaRemote` — управление через `AudioManager.dispatchMediaKeyEvent()`. Не требует разрешений. MVP.
- `SessionMediaRemote` — управление через `MediaController` + чтение метаданных. Требует `NotificationListenerService`. Sprint 7.

**Причина:** Базовые команды работают сразу. Информационные команды требуют отдельного разрешения.

## ADR-008 | 2026-06-30
### ServiceStateHolder как Hilt Singleton

**Решение:** `ServiceStateHolder` — Hilt singleton с `StateFlow`-ами. Сервис обновляет, ViewModel наблюдает. Без binding сервиса.

**Причина:** Чище, чем Service Binding. Нет утечек. Доступен из любого компонента через DI.

## ADR-009 | 2026-06-30
### FeedbackManager — только звуковые сигналы (без TTS) в MVP

**Решение:** `BeepFeedbackManager` использует `ToneGenerator` для трёх сигналов: активация, успех, ошибка. TTS добавляется позже как альтернативная реализация.

**Причина:** Нулевые зависимости. Мгновенное воспроизведение. `FeedbackManager` — интерфейс, поэтому `TtsFeedbackManager` добавляется без изменения логики.

## ADR-010 | 2026-06-30
### UnknownCommandLogger — CSV файл

**Решение:** Append-only CSV в `context.filesDir`. Ротация при достижении 512KB. Интерфейс `UnknownCommandLogger` позволит заменить на Room без изменения остального кода.

**Причина:** Нет зависимостей, простота. Достаточно для анализа неизвестных команд.

## ADR-011 | 2026-06-30
### Kotlin 2.0 + Compose Compiler Plugin

**Решение:** Используется `org.jetbrains.kotlin.plugin.compose` вместо `composeOptions.kotlinCompilerExtensionVersion`.

**Причина:** Стандартный подход для Kotlin 2.0+. Не требует ручного управления версией компилятора Compose.

## ADR-012 | 2026-06-30
### minSdk = 26 (Android 8.0)

**Решение:** Минимальная версия — Android 8.0 (Oreo, API 26).

**Причина:** API 26 = `startForegroundService()` обязателен (появился в API 26). Adaptive icons без PNG-фоллбэков. Достаточно широкое покрытие устройств (~95%+ активных Android устройств в 2025).

## ADR-013 | 2026-07-01
### Runtime Permissions обрабатываются в UI-слое, старт сервиса — «умная» кнопка

**Решение:** Проверка и запрос разрешений (`RECORD_AUDIO`, `POST_NOTIFICATIONS`) выполняются в `MainScreen` через `rememberLauncherForActivityResult`. Кнопка «Запустить» сначала проверяет разрешения, при необходимости показывает системный запрос и запускает сервис только после их получения. `AppPermissions` — единая точка описания требуемых разрешений.

**Причина:** Запрос разрешений требует `Activity`/Compose-контекста и не должен протекать в сервисный/доменный слой. Централизация в `AppPermissions` избавляет от дублирования и позволяет переиспользовать проверки в чек-листе главного экрана и на Debug Screen.

**Следствие:** `startForeground()` дополнительно защищён `try/catch` — даже при гонке или отзыве разрешения приложение не падает, а сервис переходит в состояние `Error`.

## ADR-014 | 2026-07-01
### DjLogBuffer — in-memory журнал для Debug Screen

**Решение:** `DjLogger` дублирует записи в объект-синглтон `DjLogBuffer`, который хранит последние ~100 записей и последнюю ошибку в `StateFlow`. Debug Screen читает эти потоки напрямую.

**Причина:** Позволяет показывать «последнюю ошибку» и «последнюю запись лога» в UI без подключения logcat и без записи на диск. Timber остаётся основным транспортом; буфер — только диагностическая витрина.

**Ограничение:** Данные не персистентны и очищаются при перезапуске процесса — этого достаточно для отладки в рамках Sprint 1.

## ADR-015 | 2026-07-01
### Навигация: iOS-style слайд через параметры `NavHost`, без сторонних библиотек

**Решение:** `enterTransition` / `exitTransition` / `popEnterTransition` / `popExitTransition` заданы напрямую на `NavHost` (Navigation Compose 2.8+): `slideIntoContainer` / `slideOutOfContainer` по горизонтали, `tween(300, FastOutSlowInEasing)`. Fade и затемнение не используются нигде.

**Причина:** Штатный API Navigation Compose уже поддерживает нужный эффект без дополнительных зависимостей. Кросс-fade по умолчанию (или его отсутствие в некоторых версиях) — источник "вспышки", о которой сообщил пользователь; явные slide-transitions устраняют её полностью.

## ADR-016 | 2026-07-01
### Media Layer реализован через framework `android.media.session.*`, без androidx.media

**Решение:** `MediaControllerRepository`, `MediaMetadataMapper` и `DjNotificationListenerService` используют исключительно платформенные классы: `android.media.session.MediaSessionManager`, `MediaController`, `PlaybackState`, `android.media.MediaMetadata`. Библиотека `androidx.media` (media-compat) не подключается.

**Причина:** `minSdk = 26` делает framework API полностью достаточным (session API появился в API 21) — добавление media-compat увеличило бы поверхность зависимостей без выигрыша в совместимости. Соответствует принципу Sprint 2 «изменения аддитивны, зависимости не меняются без необходимости».

**Следствие:** `SessionMediaRemote` — единственная реализация `MediaRemote` и `MediaStateProvider` (заменяет прежнюю прямую привязку `MediaRemote` к `KeyEventMediaRemote` из ADR-007). Транспортные команды идут через `MediaController.transportControls`; если активная сессия ещё не обнаружена (доступ к медиасессиям не выдан или плеер не запущен), `SessionMediaRemote` передаёт вызов в `KeyEventMediaRemote` как fallback — таким образом внешний контракт (`MediaRemote`/`MediaStateProvider`) не меняется, а надёжность растёт. Это досрочно закрывает объём, ранее запланированный на Sprint 7 (ADR-007), по прямому решению из брифа Sprint 2.

## ADR-017 | 2026-07-01
### `MediaPlaybackState.hasAlbumArt: Boolean` вместо хранения `Bitmap`

**Решение:** Наличие обложки трека передаётся булевым флагом, а не самим изображением.

**Причина:** `Bitmap` не переопределяет `equals()`/`hashCode()`, что ломает поведение `StateFlow` (эмиссии не дедуплицируются) и увеличивает риск утечек при хранении в singleton-состоянии. Рендеринг обложки не входит в объём Sprint 2 (нет пайплайна загрузки изображений); при необходимости в будущем спринте обложка будет получена заново из `MediaMetadata.getBitmap()` в момент отображения, а не через постоянное состояние.
