# DECISIONS.md — Зафиксированные архитектурные решения

Все решения в этом документе считаются окончательными.
Пересмотр возможен только по явному запросу.

---

## ADR-001 | 2026-06-30
### Приложение — голосовой пульт, не плеер

**Решение:** DJ Assistant управляет сторонними приложениями через Android MediaSession API. Собственный плеер, MediaStore-сканер, база медиатеки — отсутствуют.

**Причина:** Пользователь уже использует предпочитаемый плеер (Spotify, AIMP, VK Музыка и т.д.). Приложение не должно конкурировать с ними.

---

## ADR-002 | 2026-06-30
### Multi-module Gradle: 6 модулей

**Решение:** `app`, `core`, `data`, `feature`, `service`, `ui`

**Причина:** Достаточно для принудительного разделения слоёв без излишней сложности. Параллельная компиляция Gradle. Чёткие границы зависимостей.

**График зависимостей:**
```
app → [core, data, feature, service, ui]
ui → [core, data, feature, service]
service → [core, feature]
feature → [core, data]
data → [core]
core → []
```

## ADR-003 | 2026-06-30
### Vosk вместо Porcupine для MVP

**Решение:** Vosk обрабатывает и wake word и команду в одном распознавании. Пользователь говорит "Диджей, пауза" целой фразой. Porcupine добавляется в будущем как отдельный детектор.

**Причина:** Упрощает MVP. Vosk бесплатен, имеет малую модель для русского (~50MB), поддерживает Grammar Mode.

---

## ADR-004 | 2026-06-30
### Grammar Mode Vosk (ограниченный словарь)

**Решение:** Vosk работает только в пространстве заранее известных фраз. Грамматика генерируется автоматически из `CommandRegistry`.

**Причина:** Меньше CPU, меньше ложных срабатываний, выше точность для известных команд.

**Ключевое свойство:** `GrammarBuilder.build()` итерирует `registry.allCommands` — добавление новой команды автоматически добавляет её в грамматику.

---

## ADR-005 | 2026-06-30
### Command Pattern + Registry

**Решение:** Каждая команда — отдельный класс, реализующий `DjCommand`. Все команды хранятся в `CommandRegistry`. Маршрутизация через `CommandDispatcher`.

**Причина:** Добавление новой команды = создать 1 файл + зарегистрировать в `AppModule`. Ни `IntentRecognizer`, ни `CommandDispatcher`, ни другие команды не затрагиваются.

## ADR-006 | 2026-06-30
### Отдельный слой Intent (DjIntent)

**Решение:** `IntentRecognizer` (текст → `DjIntent`) отделён от `CommandDispatcher` (`DjIntent` → выполнение).

**Причина:** Разделяет "что хочет пользователь" от "как это выполнить". Параметризованные команды ("тише на 20%") добавляются в `IntentRecognizer` без изменения слоя команд.

## ADR-007 | 2026-06-30
### Две реализации MediaRemote

**Решение:**
- `KeyEventMediaRemote` — управление через `AudioManager.dispatchMediaKeyEvent()`. Не требует разрешений. MVP.
- `SessionMediaRemote` — управление через `MediaController` + чтение метаданных. Требует `NotificationListenerService`. Sprint 7.

**Причина:** Базовые команды работают сразу. Информационные команды требуют отдельного разрешения.

## ADR-008 | 2026-06-30
### ServiceStateHolder как Hilt Singleton

**Решение:** `ServiceStateHolder` — Hilt singleton с `StateFlow`-ами. Сервис обновляет, ViewModel наблюдает. Без binding сервиса.

**Причина:** Чище, чем Service Binding. Нет утечек. Доступен из любого компонента через DI.

## ADR-009 | 2026-06-30
### FeedbackManager — только звуковые сигналы (без TTS) в MVP

**Решение:** `BeepFeedbackManager` использует `ToneGenerator` для трёх сигналов: активация, успех, ошибка. TTS добавляется позже как альтернативная реализация.

**Причина:** Нулевые зависимости. Мгновенное воспроизведение. `FeedbackManager` — интерфейс, поэтому `TtsFeedbackManager` добавляется без изменения логики.

## ADR-010 | 2026-06-30
### UnknownCommandLogger — CSV файл

**Решение:** Append-only CSV в `context.filesDir`. Ротация при достижении 512KB. Интерфейс `UnknownCommandLogger` позволит заменить на Room без изменения остального кода.

**Причина:** Нет зависимостей, простота. Достаточно для анализа неизвестных команд.

## ADR-012 | 2026-06-30
### minSdk = 26 (Android 8.0)

**Решение:** Минимальная версия — Android 8.0 (Oreo, API 26).

**Причина:** API 26 = `startForegroundService()` обязателен (появился в API 26). Adaptive icons без PNG-фоллбэков. Достаточно широкое покрытие устройств (~95%+ активных Android устройств в 2025).

## ADR-013 | 2026-07-01
### Runtime Permissions обрабатываются в UI-слое, старт сервиса — «умная» кнопка

**Решение:** Проверка и запрос разрешений (`RECORD_AUDIO`, `POST_NOTIFICATIONS`) выполняются в `MainScreen` через `rememberLauncherForActivityResult`. Кнопка «Запустить» сначала проверяет разрешения, при необходимости показывает системный запрос и запускает сервис только после их получения. `AppPermissions` — единая точка описания требуемых разрешений.

**Причина:** Запрос разрешений требует `Activity`/Compose-контекста и не должен протекать в сервисный/доменный слой. Централизация в `AppPermissions` избавляет от дублирования и позволяет переиспользовать проверки в чек-листе главного экрана и на Debug Screen.

**Следствие:** `startForeground()` дополнительно защищён `try/catch` — даже при гонке или отзыве разрешения приложение не падает, а сервис переходит в состояние `Error`.

## ADR-014 | 2026-07-01
### DjLogBuffer — in-memory журнал для Debug Screen

**Решение:** `DjLogger` дублирует записи в объект-синглтон `DjLogBuffer`, который хранит последние ~100 записей и последнюю ошибку в `StateFlow`. Debug Screen читает эти потоки напрямую.

**Причина:** Позволяет показывать «последнюю ошибку» и «последнюю запись лога» в UI без подключения logcat и без записи на диск. Timber остаётся основным транспортом; буфер — только диагностическая витрина.

**Ограничение:** Данные не персистентны и очищаются при перезапуске процесса — этого достаточно для отладки в рамках Sprint 1.

## ADR-015 | 2026-07-01
### Навигация: iOS-style слайд через параметры `NavHost`, без сторонних библиотек

**Решение:** `enterTransition` / `exitTransition` / `popEnterTransition` / `popExitTransition` заданы напрямую на `NavHost` (Navigation Compose 2.8+): `slideIntoContainer` / `slideOutOfContainer` по горизонтали, `tween(300, FastOutSlowInEasing)`. Fade и затемнение не используются нигде.

**Причина:** Штатный API Navigation Compose уже поддерживает нужный эффект без дополнительных зависимостей. Кросс-fade по умолчанию (или его отсутствие в некоторых версиях) — источник "вспышки", о которой сообщил пользователь; явные slide-transitions устраняют её полностью.

## ADR-016 | 2026-07-01
### Media Layer реализован через framework `android.media.session.*`, без androidx.media

**Решение:** `MediaControllerRepository`, `MediaMetadataMapper` и `DjNotificationListenerService` используют исключительно платформенные классы: `android.media.session.MediaSessionManager`, `MediaController`, `PlaybackState`, `android.media.MediaMetadata`. Библиотека `androidx.media` (media-compat) не подключается.

**Причина:** `minSdk = 26` делает framework API полностью достаточным (session API появился в API 21) — добавление media-compat увеличило бы поверхность зависимостей без выигрыша в совместимости. Соответствует принципу Sprint 2 «изменения аддитивны, зависимости не меняются без необходимости».

**Следствие:** `SessionMediaRemote` — единственная реализация `MediaRemote` и `MediaStateProvider` (заменяет прежнюю прямую привязку `MediaRemote` к `KeyEventMediaRemote` из ADR-007). Транспортные команды идут через `MediaController.transportControls`; если активная сессия ещё не обнаружена (доступ к медиасессиям не выдан или плеер не запущен), `SessionMediaRemote` передаёт вызов в `KeyEventMediaRemote` как fallback — таким образом внешний контракт (`MediaRemote`/`MediaStateProvider`) не меняется, а надёжность растёт. Это досрочно закрывает объём, ранее запланированный на Sprint 7 (ADR-007), по прямому решению из брифа Sprint 2.

## ADR-017 | 2026-07-01
### `MediaPlaybackState.hasAlbumArt: Boolean` вместо хранения `Bitmap`

**Решение:** Наличие обложки трека передаётся булевым флагом, а не самим изображением.

**Причина:** `Bitmap` не переопределяет `equals()`/`hashCode()`, что ломает поведение `StateFlow` (эмиссии не дедуплицируются) и увеличивает риск утечек при хранении в singleton-состоянии. Рендеринг обложки не входит в объём Sprint 2 (нет пайплайна загрузки изображений); при необходимости в будущем спринте обложка будет получена заново из `MediaMetadata.getBitmap()` в момент отображения, а не через постоянное состояние.

## ADR-018 | 2026-07-01
### Позиция трека вычисляется локально, без повторных запросов к MediaSession

**Решение:** `MediaControllerRepository` кэширует последний `MediaMetadata`/`PlaybackState`, полученный через параметры `MediaController.Callback` (`onMetadataChanged`/`onPlaybackStateChanged`), в `snapshots: Map<MediaController, Snapshot>`. Локальный тикер на `Dispatchers.Main` (интервал 300 мс) вычисляет отображаемую позицию по формуле `PlaybackState.position + (SystemClock.elapsedRealtime() - lastPositionUpdateTime) × playbackSpeed` — без единого дополнительного обращения к `MediaController`/`MediaSession`. Тикер запускается только когда активная сессия воспроизводит (`isPlaying == true`) и останавливается немедленно на паузе.

**Причина:** `MediaController.getPlaybackState()`/`getMetadata()` — синхронные вызовы через Binder к процессу плеера; опрашивать их каждые 250–300 мс означало бы постоянную межпроцессную нагрузку. Кэширование снимка из колбэка (доставляется уже с нужными данными) и локальная экстраполяция времени — стандартный паттерн, которым пользуются Android Auto и Spotify Connect для плавного прогресс-бара.

**Следствие:** `MediaMetadataMapper.map()` больше не принимает `MediaController` — только `packageName`, кэшированные `metadata`/`playbackState` и `appName`, что делает маппер чистой функцией без побочных IPC-вызовов.

## ADR-019 | 2026-07-01
### `PlaybackSource` — диагностика способа взаимодействия с плеером

**Решение:** `MediaPlaybackState.playbackSource: PlaybackSource` принимает одно из трёх значений: `MEDIA_SESSION` (есть активный `MediaController`), `KEY_EVENT_FALLBACK` (сессии нет, но `AudioManager.isMusicActive == true` — команды дойдут через медиа-клавиши) или `NO_ACTIVE_SESSION` (ни сессии, ни звука). Значение вычисляется в `MediaControllerRepository.recomputeState()` и отображается в Debug Screen.

**Причина:** Без этого поля тестировщику/разработчику не видно, почему конкретная voice/UI-команда сработала или нет — эта диагностика напрямую запрошена в финальной полировке Sprint 2 как способ сразу понимать текущий механизм взаимодействия с плеером.

## ADR-020 | 2026-07-01
### Vosk интегрирован через официальный `vosk-android` + JNA, модель — не бандлится

**Решение:** `VoskSpeechRecognizer` использует `com.alphacephei:vosk-android` (+ `net.java.dev.jna:jna` с классификатором `@aar`), подключённые через собственный Maven-репозиторий `https://alphacephei.com/maven/`, добавленный в `settings.gradle.kts`. Сама офлайн-модель (например, `vosk-model-small-ru-0.22`, ~45 МБ) в репозиторий НЕ включается — она должна быть добавлена разработчиком в `feature/src/main/assets/model/` перед сборкой.

**Причина:** Бинарная модель — это лицензируемый сторонний артефакт, а не исходный код проекта; хранить его в git невозможно/нежелательно (размер, обновляемость, повторное распространение). `VoskModelProvisioner` копирует модель из assets во внутреннее хранилище приложения при первом запуске — целиком локальная операция, не нарушающая требование «без интернета» даже на первом старте.

**Следствие:** В песочнице сборки этого агента (без интернета для скачивания модели и без Android SDK для запуска на устройстве) итоговый сценарий «сказать „Пауза" → музыка ставится на паузу» не мог быть прогнан end-to-end. Debug Screen корректно показывает «Модель Vosk не найдена» в этом состоянии — само это поведение и есть часть требований Sprint 3 (раздел «Ошибки»/диагностика), а не обход проблемы.

## ADR-021 | 2026-07-01
### Источник фраз для распознавания — `commands.json`, не хардкод в командах

**Решение:** Фразы, ведущие к каждому `DjIntent`, хранятся в `feature/src/main/assets/commands.json` (`{"PAUSE": ["пауза", "стоп", ...], ...}`) и загружаются `VoiceCommandConfigLoader` (кэш через `by lazy`). `KeywordIntentRecognizer` и `GrammarBuilder` читают эту конфигурацию напрямую. `DjCommand.triggers` и `CommandRegistry.findByTrigger()` удалены — они были единственным потребителем старых хардкод-списков и стали мёртвым кодом после переноса источника истины в JSON.

**Причина:** Прямой запрос пользователя (Sprint 3): синонимы добавляются правкой JSON, без пересборки логики; в будущем пользовательские команды и подключение локальной языковой модели становятся возможны без изменения структуры `IntentRecognizer`/`GrammarBuilder` — меняется только то, как заполняется `Map<String, List<String>>`, а не то, как он используется.

**Следствие:** Команды `ArtistCommand`, `IsPlayingCommand`, `VolumeUpCommand`, `VolumeDownCommand`, `VolumeQueryCommand` остаются зарегистрированными в `CommandRegistry` (доступны по `findByIntent`), но не имеют записи в `commands.json` — голосом их вызвать нельзя, пока кто-то не добавит фразы в конфиг. Это осознанно: Sprint 3 явно исключает голосовое управление громкостью, а появление синонимов для informational-команд оставлено на будущее без architecture rewrite.

## ADR-022 | 2026-07-01
### `VoiceEngine`/`DjVoiceService` живут в `:service`, а не в `:feature`

**Решение:** Оркестрация голосового пайплайна (`VoiceEngine`) и его Android-обёртка (`DjVoiceService`, обычный bound Service, не foreground) размещены в модуле `:service`, рядом с `DjForegroundService`/`ServiceStateHolder`. `DjForegroundService` запускает `DjVoiceService` вместе с собой (`startForegroundSafely()`) и останавливает вместе с собой (`stopServiceCleanly()`).

**Причина:** Граф зависимостей проекта (`service → feature`, не наоборот, см. ADR-002) не позволяет `feature/voice` знать о `ServiceStateHolder`/`ServiceMode`, а `VoiceEngine` обязан обновлять оба вида состояния — сервисное (`ServiceMode.Listening/Recognizing/Processing`) и голосовое (`VoiceStateHolder`). Дублировать состояние или создавать обратную зависимость `feature → service` было бы нарушением уже принятой архитектуры. `DjVoiceService` — обычный (не foreground) Service: ему не нужно собственное уведомление, он существует, пока процесс уже держится живым за счёт `DjForegroundService`.

**Следствие:** `feature/voice` при этом остаётся полностью независимым от Media Layer в буквальном смысле — ни один файл в `feature/voice` не импортирует `feature/media`. Единственная точка, где голосовой пайплайн касается плеера — вызов уже существующего `CommandDispatcher.dispatch()` внутри `VoiceEngine`, тот же самый публичный интерфейс, которым Sprint 1/2 пользовались всегда.

## ADR-023 | 2026-07-01
### Wake word отложен: `stripWakeWord()` вызывается как no-op уже сейчас

**Решение:** `KeywordIntentRecognizer.recognize()` вызывает `commandText.stripWakeWord()` (утилита `core`, существующая с Sprint 1) перед сопоставлением с `commands.json`, даже притом что Sprint 3 не требует и не использует активационную фразу. Если префикса "диджей"/"dj" нет, вызов — no-op (текст не меняется).

**Причина:** Прямое требование брифа Sprint 3 — «архитектура должна позволять добавить wake word позже, не переписывая существующий код». Сохранение вызова `stripWakeWord()` уже сейчас гарантирует, что будущий gate (например, `if (!text.containsWakeWord()) return` перед вызовом `IntentRecognizer.recognize()` в `VoiceEngine.handleRecognition()`) добавляется одной проверкой, без изменения матчинга фраз.

## ADR-024 | 2026-07-01
### Исправлен баг: `DjForegroundService` не возобновлялся после `START_STICKY`-перезапуска

**Решение:** Раньше `onStartCommand()` с `intent == null` (именно так система пересоздаёт STICKY-сервис после уничтожения процесса) обрабатывался веткой `else`, которая вызывала `stopSelf()` — то есть сервис немедленно останавливал себя вместо возобновления. Теперь null-интент обрабатывается так же, как `ACTION_START`: `startForegroundSafely()` вызывается повторно.

**Причина:** Обнаружено при реализации требования Sprint 3 «Voice Service должен автоматически восстанавливаться после перезапуска сервиса» — без этого исправления `DjForegroundService` (а вместе с ним и `DjVoiceService`) не переживал перезапуск процесса вовсе, что делает восстановление голосового пайплайна невозможным в принципе. Это баг-фикс, обнаруженный по ходу работы над архитектурным требованием, а не отдельная новая возможность.

## ADR-025 | 2026-07-01
### `WakeWordDetector` — отдельная абстракция активации, не встроена в `SpeechRecognizer`

**Решение:** Активация вынесена в собственный интерфейс `WakeWordDetector` (`suspend fun waitForWakeWord(audioFlow): Boolean`), а не реализована как ещё один режим `SpeechRecognizer`. Единственная реализация — `VoskWakeWordDetector`, использующая тот же `SpeechRecognizer` с урезанным словарём (`vocabulary` параметр, добавленный в интерфейс `SpeechRecognizer.startListening()`).

**Причина:** Прямое требование Sprint 3.1 — «архитектура должна позволять заменить механизм активации без изменения Media Layer», и «не привязывать реализацию к Vosk». `VoiceEngine` зависит только от `WakeWordDetector`, поэтому подключение Porcupine/OpenWakeWord — это добавление новой реализации интерфейса и одна строка в `AppModule` (`@Binds`), без изменений в `VoiceEngine`, `IntentRecognizer` или Media Layer.

**Следствие:** `SpeechRecognizer.startListening()` получил необязательный параметр `vocabulary: List<String>? = null` — null использует полную командную грамматику (`GrammarBuilder`, поведение Sprint 3 не изменилось), non-null подставляет любой список слов напрямую. Это расширение интерфейса, а не поломка обратной совместимости — существующие вызовы без параметра продолжают работать как раньше.

## ADR-026 | 2026-07-01
### Confidence threshold проверяется в `VoiceEngine` до `IntentRecognizer`, не после

**Решение:** `VoiceEngine.handleRecognition()` сравнивает `RecognitionResult.confidence` с `DjSettings.voskConfidenceThreshold` сразу после получения результата от Vosk, до вызова `IntentRecognizer.recognize()`. При отказе ни Intent Parser, ни `CommandDispatcher` не вызываются вовсе — сразу пишется `VoiceCommandLogEntry` с `rejectReason`.

**Причина:** Порог confidence — это фильтр качества распознавания речи, а не логики распознавания намерения; помещать проверку после `IntentRecognizer` означало бы тратить цикл на сопоставление текста, который и так будет отброшен. Кроме того, бриф явно требует «если confidence ниже — команда НЕ выполняется», то есть отказ должен происходить раньше любого потенциального побочного эффекта.

**Значение по умолчанию:** `0.8f` (80%), диапазон 50–95% — оба значения зафиксированы явно в брифе Sprint 3.1.

## ADR-027 | 2026-07-01
### Два режима прослушивания живут в `VoiceEngine` как явный цикл `while`, без второго сервиса

**Решение:** `VoiceListeningMode.CONTINUOUS`/`WAKE_WORD` — не два отдельных Android-компонента, а два пути внутри одного `VoiceEngine.runPipeline()`: внешний `while (engineScope.isActive)` вызывает `runContinuousSession()` либо `runWakeWordSession()` в зависимости от `currentListeningMode`, которое любая сессия может изменить (голосовой командой) и тем самым завершить текущую сессию досрочно (через `takeWhile { !switchRequested }`).

**Причина:** Оба режима используют один и тот же `AudioRecorder`/`SpeechRecognizer`/`WakeWordDetector` набор зависимостей и должны делить один и тот же аудиопоток (`shareIn(engineScope, SharingStarted.Eagerly)`), чтобы не перезапускать `AudioRecord` при каждом переключении режима. Два отдельных `DjVoiceService`-подобных компонента только усложнили бы синхронизацию без выгоды.

**Следствие:** Диалоговое окно (`WAKE_WORD` → полное распознавание на `dialogWindowSeconds`) реализовано как дочерний `Job` со сторожевым циклом (`delay(300)` + сравнение времени последней активности), который отменяется по таймауту — отмена `Job.cancel()` не считается ошибкой для охватывающего `coroutineScope { }`, поэтому переход обратно к ожиданию wake word происходит без лишних исключений.

## ADR-028 | 2026-07-01
### `CommandContext` несёт фактический `DjIntent`, не только тип

**Решение:** `CommandContext` получил поле `intent: DjIntent` — сматченный экземпляр интента (не просто использованный для поиска команды в `CommandRegistry.findByIntent()` по классу). `SetVolumePercentCommand` читает `(context.intent as? DjIntent.SetVolumePercent)?.percent` для получения параметра.

**Причина:** `SetVolumePercent(percent: Int)` — первая параметризованная MVP-команда; без доступа к фактическому интенту команда не могла бы узнать, какой процент запросил пользователь (шаблонный `intent` в `DjCommand.intent` существует только для сопоставления типов и хранит фиктивное значение `0`).

**Следствие:** Все остальные команды (`PauseCommand`, `NextTrackCommand` и т.д.) не читают `context.intent` — им это не нужно, так как для них весь смысл исчерпывается типом. Расширение контракта обратно совместимо: старые команды не требуют изменений.

## ADR-029 | 2026-07-01 (superseded by ADR-030/031)
### Bluetooth-микрофон — автоматический выбор без ручного переключателя

**Решение:** `AndroidAudioRecorder` при каждом запуске ищет подключённое Bluetooth SCO-устройство через `AudioManager.getDevices(GET_DEVICES_INPUTS)`; если найдено — активирует `startBluetoothSco()` и назначает `AudioRecord.preferredDevice`, иначе использует встроенный микрофон. Активный источник виден в Debug Screen через `AudioRecorder.activeInputSource`. Ручной переключатель ("Auto/Built-in/Bluetooth") в Settings не добавлен.

**Причина:** Бриф Sprint 3.1 разрешал этот вариант явно: «если ручной выбор невозможен из-за ограничений Android API — оставить автоматический выбор и вывести информацию о текущем источнике записи в Debug Screen». Android не предоставляет декларативного публичного API уровня приложения для гарантированного ручного выбора входного устройства (в отличие от вывода, где `AudioManager`/`MediaRouter` дают больше контроля) без более глубокой работы с `AudioDeviceCallback`/`AudioPlaybackConfiguration`, которая выходит за рамки этого спринта и не может быть протестирована в среде без реального Bluetooth-устройства.

**Заменено:** пользователь указал, что это решение держало SCO активным всё время работы движка (включая ожидание wake word), оставляя Bluetooth-гарнитуру в режиме "звонка" дольше необходимого. См. ADR-030 и ADR-031 для редизайна.

## ADR-030 | 2026-07-01
### `MicrophoneSource` — явный выбор пользователя вместо скрытого автовыбора

**Решение:** Добавлена настройка `DjSettings.microphoneSource: MicrophoneSource` (`AUTO` / `PHONE` / `BLUETOOTH`, по умолчанию `AUTO`), персистится через `DataStoreSettingsRepository`, выбирается тремя чипами в `SettingsScreen`. `AUTO` и `PHONE` ведут себя идентично — оба никогда не вызывают Bluetooth SCO API вообще. Только явный выбор `BLUETOOTH` включает логику Bluetooth-роутинга.

**Причина:** Прямое требование: «In Auto mode, prefer the phone microphone unless Bluetooth input is explicitly required». Реализовано буквально и консервативно — раз обычный телефонный микрофон всегда доступен, «явно требуется Bluetooth» интерпретируется как «пользователь сам выбрал Bluetooth», а не как эвристика на основе того, что где-то рядом есть подключённая гарнитура. Это устраняет и прежнюю жалобу: по умолчанию (AUTO) приложение теперь никогда не трогает Bluetooth SCO.

## ADR-031 | 2026-07-01
### Bluetooth SCO — решение уровня сессии записи, а не рекордера

**Решение:** `AudioRecorder.start(allowBluetooth: Boolean = false)` — Bluetooth больше не выбирается автоматически внутри `AndroidAudioRecorder`; вызывающая сторона (`VoiceEngine`) решает для каждой конкретной сессии записи, разрешён ли Bluetooth. `VoiceEngine` убрал единый `shareIn`-разделяемый аудиопоток на весь срок жизни движка (Sprint 3.1) и вместо этого открывает отдельную сессию записи для каждой смысловой фазы:
- Ожидание wake word (Wake Mode) — всегда `allowBluetooth = false`, без исключений, независимо от настройки: это единственное по-настоящему простаивающее состояние, и оно не должно держать гарнитуру в режиме звонка.
- Диалоговое окно (Wake Mode) и вся сессия Continuous Mode — `allowBluetooth = resolveAllowBluetooth()` (true только если `microphoneSource == BLUETOOTH`); сессия закрывается (`audioRecorder.stop()`) сразу по завершении окна/распознавания.

Дополнительно `AndroidAudioRecorder` дожидается фактического подключения SCO (`BroadcastReceiver` на `AudioManager.ACTION_SCO_AUDIO_STATE_UPDATED`, `withTimeoutOrNull(2000мс)`) перед началом записи через Bluetooth-путь, и вызывает `stopBluetoothSco()` в `finally`-блоке сразу после остановки `AudioRecord`.

**Причина:** Прямые требования: «Do not keep Bluetooth SCO permanently active», «Only enable SCO immediately before recording a voice command», «Disable SCO immediately after recognition finishes», «Restore A2DP playback as quickly as possible», «The Voice Service must never keep Bluetooth headphones in call mode while idle». Привязка SCO к жизненному циклу конкретной сессии записи (а не к жизненному циклу всего движка) — единственный способ буквально выполнить все пять требований одновременно.

## ADR-032 | 2026-07-01
### `VoskWakeWordDetector` — предикат ожидания должен матчить только реальную wake-фразу, не любой непустой финальный результат

**Проблема:** Несмотря на архитектурное разделение сессий записи (ADR-031), пользователь на реальном устройстве по-прежнему наблюдал, что Wake Mode «ощущается как Continuous Mode», а Bluetooth-качество деградирует. Трассировка кода показала: `waitForWakeWord()` завершал `Flow.first { it.isFinal && it.text.isNotBlank() }` на ЛЮБОМ финальном результате Vosk. В Grammar Mode (используется здесь намеренно — маленький словарь дешевле полного) Vosk возвращает буквальную непустую строку `"[unk]"` для любой речи/шума вне заданного словаря. Значит, почти любой звук завершал ожидание с `detected = false`, и `VoiceEngine.runWakeWordSession()` тут же пересоздавал сессию (новый `AudioRecord`, новый `Recognizer`, в Wake Mode — с новым Bluetooth SCO хендшейком, если выбран Bluetooth) — цикл перезапусков, а не «движок никогда не спит».

**Решение:** Предикат сужен до `.first { it.isFinal && WAKE_PHRASES.any { phrase -> it.text.contains(phrase) } }`. Теперь `"[unk]"` и пустые финальные результаты не завершают ожидание — `AudioRecord`/`Recognizer` остаются открытыми и тихо ждут, пока не прозвучит реальная wake-фраза. Это не проверка присутствия речи, а условие завершения flow — не нужно менять ни `AudioRecorder`, ни `SpeechRecognizer`, только предикат в `WakeWordDetector`-реализации, за интерфейсом, который для этого и существует.

**Причина:** Пользователь потребовал буквально: «Проверить это по коду. Если текущая реализация действительно держит VoiceEngine активным постоянно — исправить». Ошибка была не в том, что движок «никогда не спит» в смысле не освобождает ресурсы (ADR-031 это гарантирует), а в том, что сессия ожидания слишком часто и без пользы пересоздавалась — с точки зрения пользователя оба симптома неотличимы («звучит как будто всегда слушает»).

## ADR-033 | 2026-07-01
### Оверлей Listening-режима — чистые Android View + WindowManager, не Compose

**Решение:** `VoiceOverlayController` (`service/overlay`) реализован на обычных `View`/`LinearLayout`/`TextView`, программно создаваемых в коде, и добавляется в `WindowManager` как `TYPE_APPLICATION_OVERLAY`-окно с флагами `FLAG_NOT_TOUCHABLE | FLAG_NOT_FOCUSABLE | FLAG_LAYOUT_NO_LIMITS`. Анимации — стандартные `View.animate()` (fade/scale, `OvershootInterpolator`) и `ValueAnimator` (пульсация индикатора), без `androidx.dynamicanimation` и без Compose.

**Причина:** Архитектурная граница проекта: Compose используется только в `:ui`; `:service` намеренно остаётся Compose-free (см. существующую документацию модулей). Оверлей — это floating-окно поверх ВСЕХ приложений, а не часть Activity/Compose-дерева самого DJ Assistant, так что привязывать его к Compose не было бы естественно даже без этого ограничения. `SYSTEM_ALERT_WINDOW` — специальное разрешение (не runtime-permission), поэтому добавлен `OverlayAccess` helper в `ui/permissions` по образцу уже существующего `NotificationAccess`, и карточка в `SettingsScreen` для его выдачи.

**Ограничение:** Не проверено на реальном устройстве (нет Android SDK/дисплея в этой среде) — визуальный вид, плавность анимаций и корректность работы `WindowManager`-флагов должны быть подтверждены пользователем.

**Ограничение:** в Continuous Mode с явно выбранным `BLUETOOTH` SCO неизбежно остаётся активным на всё время сессии — этот режим по определению не имеет состояния простоя (движок всегда что-то распознаёт). Это осознанный компромисс, а не недосмотр: пользователь явно выбирает Bluetooth, зная о continuous-семантике.

## ADR-034 | 2026-07-01
### Оверлей — вся работа с View/WindowManager обязана выполняться на главном потоке

**Проблема:** Sprint 3.2 ввёл `VoiceOverlayController`, вызываемый из `VoiceEngine`, чей `engineScope` работает на `Dispatchers.IO` — фоновом потоке без `Looper`. Все методы контроллера (`show`/`updateStatus`/`updateCountdown`/`hide`) мутировали `View` и вызывали `WindowManager.addView()`/`removeView()` прямо инлайн, на вызывающем потоке. `WindowManager.addView()` (как и создание `Handler`/аниматоров, использующих Choreographer) требует `Looper` на текущем потоке — без него бросается необработанное исключение. Поскольку `show()` впервые вызывается ровно в момент обнаружения wake word, приложение падало детерминированно при первом произнесении "Диджей", разваливая процесс целиком, а не только голосовой пайплайн.

**Решение:** Каждый публичный метод `VoiceOverlayController` — это тонкая обёртка, которая передаёт свою реальную работу в приватный `runOnMain { ... }`, отправляющий блок в `Handler(Looper.getMainLooper())` (либо выполняющий его инлайн, если вызов и так уже пришёл с главного потока). Всё изменяемое состояние (`overlayView`, `statusText`, `countdownText`, `micDot`, `pulseAnimator`) читается и пишется исключительно из этих постовых блоков, так что параллельного доступа с разных потоков в принципе не бывает — не нужна отдельная синхронизация поверх однопоточной очереди Handler'а. Добавлен `hideImmediately()` (без анимации) для использования в `VoiceEngine.stop()`, где нужно решительное, а не отложенное закрытие.

**Причина:** Прямое требование пользователя: «Исправить падение приложения при произнесении "Диджей" (найти и устранить первопричину, а не обходить её)». Перенос выполнения на главный поток устраняет причину падения полностью — try/catch вокруг вызовов лишь замаскировал бы симптом (оверлей продолжал бы не работать), а не решил задачу.

## ADR-035 | 2026-07-01
### Ошибки Voice Layer локализуются по этапу и никогда не приводят к падению приложения

**Решение:** `VoiceEngine` хранит `@Volatile currentStage: String`, обновляемую перед каждым значимым шагом конвейера (`waiting_wake_word`, `wake_word_detection`, `overlay_show`, `dialog_window`, `recognition_processing`, `command_dispatch` и т.д.). Основной цикл (`runPipeline()`) оборачивает каждую сессию в `try/catch(e: Exception)` (с явным `catch (e: CancellationException) { throw e }` перед ним, чтобы не глотать отмену корутин): любое исключение логируется через `DjLogger.voiceError("Ошибка на этапе '$stage'", e)` (автоматически попадает в `DjLogBuffer.lastError`, уже отображаемый на Debug Screen) и переводит `VoiceEngineState` в `Error("[$stage] ...")`. Ресурсы (`AudioRecorder.stop()`, `voiceOverlayController.hideImmediately()`) освобождаются в самом `catch`-блоке, а цикл продолжает работу (с секундной паузой) вместо падения. `engineScope` дополнительно снабжён `CoroutineExceptionHandler` как последним рубежом защиты. `handleRecognition()` использует `try/finally`, гарантированно возвращающий `VoiceEngineState.Listening`, чтобы ни одна ветка (включая исключение) не могла оставить состояние «зависшим» на `Processing`/`Executing`.

**Причина:** Прямое требование: «Добавить обработку исключений с записью причины в Debug Screen, чтобы при любых сбоях было видно, на каком этапе произошла ошибка». Решено переиспользованием уже существующего канала диагностики (`DjLogBuffer`/`DjLogger.voiceError`) вместо добавления нового UI-компонента — тег этапа делает единственное сообщение достаточно информативным.

## ADR-036 | 2026-07-01
### Sprint 3.2 не считается завершённым до прохождения полного чек-листа на устройстве

**Решение:** Несмотря на то, что весь код Sprint 3.2 был написан, закоммичен и задокументирован как «завершённый», пользователь по результатам тестирования на реальном устройстве явно объявил, что спринт не завершён, и запросил отдельный стабилизационный спринт (3.3) без новых функций. ROADMAP.md/PROJECT_STATE.md обновлены, чтобы отражать это: Sprint 3.2 помечен как ⚠️ (не стабилен на устройстве), а Sprint 3.3 — как 🔧 («код готов, ждёт проверки»), а не ✅. Итоговое «завершено» для обоих спринтов будет проставлено только после того, как пользователь подтвердит успешное прохождение полного чек-листа на реальном устройстве.

**Причина:** В этой среде агента нет Android SDK, физического устройства и Bluetooth-гарнитуры — значит, ни один спринт, зависящий от рантайм-поведения на устройстве, не может быть честно помечен как «завершён» самим агентом. Прямая цитата пользователя: «Только после успешного прохождения полного чек-листа на реальном устройстве считать Sprint 3.2 завершённым» — зафиксирована как процессное правило, а не разовое замечание, и должна применяться к будущим спринтам с аналогичными рисками.
